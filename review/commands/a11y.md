# /review:a11y

Perform a WCAG 2.1/2.2 accessibility audit covering all four POUR principles. Produces findings mapped to specific success criteria with severity ratings, reproduction steps, and remediation guidance.

**Rule: findings only, no code edits.** This command produces a report. The user decides what to fix.

**Rule: read-only browser sessions.** No clicks that mutate state (form submits, deletes). Navigation and inspection only.

---

## Flow

### 1. Detect verification mode

Determine whether to use live browser verification or static analysis.

**Browser mode prerequisites (all must be true):**
- Playwright MCP tools are available (test by checking tool availability)
- A dev server URL is confirmed

**Dev server detection order:**
1. Check if a URL was provided as the argument
2. Check CLAUDE.md or project docs for a dev server command or URL
3. Check `package.json` scripts for `dev`, `start`, or `serve`
4. Ask the user: "What URL is the dev server running on?" (provide a skip option for static-only mode)

> **Deferred tool note:** Before calling `AskUserQuestion`, call `ToolSearch` with query `"select:AskUserQuestion"` to load the tool schema.

If Playwright MCP is not connected or no dev server is available: fall back to static analysis mode.

### 2. Detect UI code

Before proceeding, verify the target contains UI code (HTML, JSX, TSX, Vue, Svelte, Angular templates, CSS).

```bash
# Check for UI file types
git diff --name-only --cached | grep -E '\.(html|jsx|tsx|vue|svelte|css|scss)$'
```

If no UI files are found in the target scope, scan the project root for common frontend indicators:

```
package.json (react, vue, svelte, angular dependencies)
*.html files
src/**/*.{jsx,tsx,vue,svelte}
```

If no UI components are detected at all, exit cleanly:

> No UI components detected. This command targets frontend code.

Do NOT proceed with the audit. Do NOT suggest workarounds or alternative checks. This is a clean exit, not an error.

### 3. Resolve target scope

**If a URL is provided:** use it directly for browser mode.

**If a file path or directory is provided:** identify all UI-related files for static analysis; if browser mode is active, determine which routes/pages to test.

**If a PR number is provided:** extract changed UI files via `git diff`.

**If no argument is provided:** check for staged or recent UI changes.

```bash
git diff --name-only --cached | grep -E '\.(html|jsx|tsx|vue|svelte|css|scss)$'
```

If still nothing: ask the user to provide a target.

### 4. Execute audit

Run the audit using the detected mode.

## Browser Mode

When Playwright MCP is available and a dev server is confirmed, perform live verification against the running DOM.

### Phase 1: Perceivable

Test that all content is presentable to users in ways they can perceive.

**Non-text Content (WCAG 1.1.1 — Level A)**
- Use `browser_snapshot` to inspect the accessibility tree for all `<img>`, `<svg>`, `<canvas>`, and icon elements
- Verify informative images have descriptive `alt` text
- Verify decorative images have `alt=""` or `aria-hidden="true"`
- Verify icon-only buttons have an accessible name via `aria-label` or visually-hidden text

**Information and Relationships (WCAG 1.3.1 — Level A)**
- Verify heading hierarchy is logical (no skipped levels)
- Verify lists use semantic elements (`<ul>`, `<ol>`, `<dl>`)
- Verify tables use `<th>` with `scope` attributes
- Verify form elements are associated with labels via `for`/`id`, `aria-label`, or `aria-labelledby`

**Meaningful Sequence (WCAG 1.3.2 — Level A)**
- Verify DOM reading order matches visual order
- Check for CSS-only visual reordering that diverges from DOM order

**Sensory Characteristics (WCAG 1.3.3 — Level A)**
- Verify instructions do not rely solely on shape, color, size, or spatial position

**Use of Color (WCAG 1.4.1 — Level A)**
- Verify color is not the sole means of conveying information (error states, required fields, charts)

**Contrast Analysis (WCAG 1.4.3 and 1.4.11 — Level AA)**

Use `browser_evaluate` to extract and calculate contrast ratios:

```javascript
// Extract computed foreground and background colors
const fg = window.getComputedStyle(element).color;
const bg = window.getComputedStyle(element).backgroundColor;
```

Thresholds:
- Normal text (< 18pt or < 14pt bold): minimum 4.5:1
- Large text (>= 18pt or >= 14pt bold): minimum 3:1
- UI component boundaries and graphical objects: minimum 3:1

Skip: disabled elements, decorative elements, logotype text.

**Resize and Reflow (WCAG 1.4.4 and 1.4.10 — Level AA)**
- Use `browser_resize` to test at 200% zoom — verify no content or functionality is lost
- Resize viewport to 320px width — verify content reflows without horizontal scrolling

**Text Spacing (WCAG 1.4.12 — Level AA)**
- Use `browser_evaluate` to inject spacing overrides and verify no content is clipped:

```javascript
document.documentElement.style.cssText = `
  line-height: 1.5 !important;
  letter-spacing: 0.12em !important;
  word-spacing: 0.16em !important;
`;
```

**Content on Hover or Focus (WCAG 1.4.13 — Level AA)**
- Verify tooltip/popover content is dismissible (Escape key), hoverable, and persistent

### Phase 2: Operable

Test that all UI functionality is operable via keyboard.

**Keyboard Navigation**
1. Press Tab repeatedly, capturing `browser_snapshot` after each to record focus position
2. Verify all interactive elements receive focus
3. Verify non-interactive elements do not receive focus
4. Test Enter on links and buttons, Space on buttons and checkboxes
5. Test Escape to close modals, dropdowns, popovers
6. Test Arrow keys within composite widgets (menus, tabs, radio groups)
7. Test Shift+Tab reverse navigation
8. Verify focus returns to trigger after closing a modal

**Focus Visibility (WCAG 2.4.7 — Level AA)**
- Use `browser_evaluate` to check computed focus styles (outline, box-shadow)
- Flag elements where focus produces no visible style change

**Touch Target Size (WCAG 2.5.8 — Level AA)**
- Resize to 375px mobile viewport
- Use `browser_evaluate` to measure bounding rects
- Flag interactive elements with width or height < 24px

**Skip Navigation (WCAG 2.4.1 — Level A)**
- Verify a skip-to-main-content link is the first focusable element

**Focus Order (WCAG 2.4.3 — Level A)**
- Verify focus order follows visual reading order
- Flag `tabindex` values > 0

**Link Purpose (WCAG 2.4.4 — Level A)**
- Flag "click here", "read more", "learn more" without additional context

### Phase 3: Understandable

Test that content and operation are understandable.

**Language (WCAG 3.1.1 — Level A)**
- Verify `<html lang="...">` is present and correct

**On Focus / On Input (WCAG 3.2.1 and 3.2.2 — Level A)**
- Verify focusing or changing a field does not trigger unexpected context change

**Error Identification (WCAG 3.3.1 — Level A)**
- If forms are present, trigger validation and verify errors are identified in text, associated with the field

**Labels or Instructions (WCAG 3.3.2 — Level A)**
- Verify all form inputs have visible labels

**Accessible Authentication (WCAG 3.3.8 — Level AA)**
- Verify authentication flows do not require cognitive function tests without an alternative

### Phase 4: Robust

Test that content is interpreted reliably by assistive technologies.

**Accessibility Tree Inspection**
1. Use `browser_snapshot` to capture the full accessibility tree
2. For every interactive element, verify:
   - Accessible name is present and descriptive
   - Role matches the widget's behavior
   - Required ARIA states are present (aria-expanded, aria-selected, aria-checked)
   - States update dynamically on interaction
3. Check for:
   - `aria-hidden="true"` on focusable elements
   - `role="presentation"` on elements with focusable descendants
   - Missing `aria-expanded` on disclosure buttons
   - Missing `aria-label` on icon buttons
   - Duplicate `id` attributes

**Name, Role, Value (WCAG 4.1.2 — Level A)**
- Verify custom widgets expose name, role, value, and states to the accessibility tree

**Status Messages (WCAG 4.1.3 — Level AA)**
- Verify live regions use appropriate `aria-live` politeness level

## Static Mode

When Playwright MCP is unavailable or no dev server is running, analyze source code directly.

### Static analysis scope

Scan all UI files in the target for the following patterns:

**Perceivable**
- `<img>` without `alt` attribute (WCAG 1.1.1)
- Heading levels that skip (e.g., `<h1>` followed by `<h3>`) (WCAG 1.3.1)
- Form inputs without associated `<label>`, `aria-label`, or `aria-labelledby` (WCAG 1.3.1)
- Hard-coded color values without sufficient contrast (estimate from source where possible) (WCAG 1.4.3)
- Fixed pixel font sizes that prevent browser zoom scaling (WCAG 1.4.4)
- `overflow: hidden` on text containers (WCAG 1.4.4)

**Operable**
- `onClick` handlers on non-interactive elements (`<div>`, `<span>`) without `role`, `tabIndex`, and keyboard handlers (WCAG 2.1.1)
- Missing `onKeyDown`/`onKeyUp` alongside `onClick` (WCAG 2.1.1)
- `tabindex` values > 0 (WCAG 2.4.3)
- Links with generic text: "click here", "read more", "learn more", "here" (WCAG 2.4.4)
- Interactive elements smaller than 24px in CSS (WCAG 2.5.8)
- `outline: none` or `outline: 0` without a replacement focus style (WCAG 2.4.7)
- Mouse-only event handlers (`onMouseOver`, `onMouseEnter`) without keyboard equivalents (WCAG 2.1.1)

**Understandable**
- Missing `lang` attribute on `<html>` (WCAG 3.1.1)
- Form fields without visible labels (WCAG 3.3.2)
- Error messages not programmatically associated with fields (WCAG 3.3.1)

**Robust**
- `aria-hidden="true"` on focusable elements or their ancestors (WCAG 4.1.2)
- Duplicate `id` attributes in the same document scope (WCAG 4.1.1)
- ARIA roles that conflict with native semantics (e.g., `role="button"` on `<a>` without keyboard handling) (WCAG 4.1.2)
- Missing required ARIA attributes for declared roles (WCAG 4.1.2)

### Static analysis limitations

Note in the report:
> Findings are based on static source analysis and may miss runtime-rendered issues (dynamic content, computed styles, JavaScript-generated DOM). For comprehensive verification, start a dev server and re-run this command.

## Severity taxonomy

| Level | Label | Criteria |
|-------|-------|----------|
| Critical | **Critical** | WCAG Level A failure. Complete barrier to access for one or more disability categories. |
| Serious | **Serious** | WCAG Level AA failure. Significant usability barrier. |
| Moderate | **Moderate** | WCAG Level AAA opportunity or Level AA edge case. |
| Minor | **Minor** | Best practice enhancement. No WCAG criterion violated. |

## False positive exclusions

Do NOT report the following as violations:

1. **Framework-correct ARIA** — Radix UI, HeadlessUI, Reach UI, MUI with proper configuration generate correct ARIA. Verify misconfiguration before reporting.
2. **Test files and Storybook stories** — Code that never ships to users is out of scope.
3. **Third-party embedded iframes** — Note as informational ("Third-party widget at X may require separate audit") but do not count as violations.
4. **Decorative images with `alt=""`** — Correct implementation.
5. **Redundant ARIA on native elements** — `role="button"` on `<button>` is noise, not a barrier. Note only if it creates a conflict.
6. **Syntax-highlighted code blocks** — WCAG exempts stylized text.
7. **Placeholder text contrast** — Placeholder is not critical information.
8. **Disabled element contrast** — WCAG exempts inactive UI components.

**Confidence threshold:** Only report findings with >= 70% confidence of an actual barrier to access. When automated checks suggest an issue in browser mode, verify with Playwright before including.

## 5. Format findings

For each finding, include ALL of:

1. **Finding ID** — `A11Y-NNN`
2. **WCAG Criterion** — e.g., 1.4.3 Contrast (Level AA)
3. **Element** — selector or description
4. **Issue** — what is wrong and why it creates a barrier
5. **Impact** — who is affected (screen reader users, keyboard users, low vision users, etc.)
6. **Severity** — Critical, Serious, Moderate, or Minor
7. **Reproduction steps** — how to observe the issue
8. **Remediation** — specific fix with code example where applicable

Group findings by severity (Critical first).

### Clean input handling

If the target has no findings, report exactly:

> Clean run. No accessibility issues detected above the 70% confidence threshold.

Do NOT invent problems to fill a report.

## WHAT NOT TO DO

- Do NOT modify any file — this command is read-only, findings only.
- Do NOT click buttons that submit forms, delete data, or mutate state in browser mode.
- Do NOT report findings below 70% confidence.
- Do NOT flag framework-correct ARIA patterns as violations.
- Do NOT flag test files, Storybook stories, or non-shipping code.
- Do NOT flag disabled elements for contrast failures.
- Do NOT use Write or Edit tools under any circumstances.
