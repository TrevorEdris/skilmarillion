Five Claude Code plugins. Specify, design, implement, review — each step produces a concrete artifact.

Why this exists

The problem

Every prompt starts from scratch. Nothing carries forward — no spec, no design record, no review gate.

The solution

One plugin per phase, one artifact per plugin — a spec, an ADR, tested code, a findings report. Each feeds the next.

The lifecycle

Four phases, connected by artifacts. Each plugin works standalone.

Specify /plan:sdd

From a task description: testable acceptance criteria, vertical slices, TDD plan.

specs/SPEC-001-*.md
Design /arch:design

Interview-driven design. Produces ADRs, OpenAPI specs, schemas, and C4 diagrams.

adrs/001-*.md
Implement /impl:tdd

Slice-by-slice TDD from a spec. Red, green, refactor — one slice at a time.

tested, committed code
Review /review:review

Code quality, security, and accessibility — checked in parallel. Findings only.

review-report.md

Five plugins, one suite

Each plugin works standalone. Together they form the full lifecycle.

plan

Classifies tasks by size and risk, then generates a spec: acceptance criteria, vertical slices, TDD plan.

Produces
SPEC-NNN-slug.md

arch

Guided design sessions. Records trade-offs as ADRs, generates OpenAPI specs and database schemas.

Produces
ADR, OpenAPI YAML, DDL

impl

Executes a spec slice by slice: red, green, refactor. Also drives debugging and conventional commits.

Produces
Tested, committed code

review

Checks code quality, security, and accessibility in parallel. One findings report, sorted by impact.

Produces
review-report.md

skil

Routes tasks to the right plugin. Lists available commands.

Entry point
/skil:help

A task, start to finish

One feature, four phases. Each command picks up where the last left off.

1 Specify /plan:sdd "add user authentication" 
# Triaged as FEATURE, MODERATE risk
# 3 vertical slices identified

### Slice 1: Session Middleware
GIVEN an HTTP request with a valid session cookie
WHEN  the middleware runs
THEN  req.user is populated from the session store

### Slice 2: Login Endpoint
GIVEN valid credentials
WHEN  POST /auth/login
THEN  a session is created and a cookie is set

Saved to docs/auth/specs/SPEC-001-user-auth.md
Next step: /impl:tdd docs/auth/specs/SPEC-001-user-auth.md
2 Design /arch:design "session storage" 
## ADR-003: Session Storage Strategy

Context:  Auth requires server-side sessions. Options: database, Redis, signed cookies.
Decision: Redis-backed sessions. Handles horizontal scaling without sticky sessions.
Trade-off: Adds Redis dependency. Accepted: session TTL and invalidation are simpler.

Saved to docs/adrs/003-session-storage.md
Next step: /impl:tdd docs/auth/specs/SPEC-001-user-auth.md
3 Implement /impl:tdd docs/auth/specs/SPEC-001-user-auth.md 
Slice 1/3: Session Middleware

RED   session.test.ts — req.user is undefined without middleware  FAIL
GREEN session.ts — attach user from Redis session store          PASS
Suite: 14 passed, 0 failed

Slice 2/3: Login Endpoint

RED   login.test.ts — POST /auth/login returns 200 + cookie     FAIL
GREEN login.ts — validate credentials, create session           PASS
Suite: 16 passed, 0 failed

All 3 slices green. Implementation complete.
Next step: /impl:commit
4 Review /review:review

- Each slice has matching test coverage
- Session TTL prevents unbounded memory growth
- Redis connection uses pool with health checks
