A coherent lifecycle for AI-assisted development

One Claude Code plugin that replaces ad-hoc prompting with structured workflows. Specify, design, implement, review — each step produces a real artifact, not just conversation.

View on GitHub See the lifecycle

Why this exists

The problem

Each AI prompt starts from scratch. No shared context between planning and implementation. No design record. No review gate. Code ships without ever being specified, architected, or systematically reviewed.

The solution

fellowship produces artifacts that flow forward. Specs feed implementation. Implementations feed review. Every phase leaves a record. Nothing gets lost between steps.

The lifecycle

Four phases, connected by artifacts. Each phase produces a concrete output that feeds the next.

The fellowship plugin

Install once. Six commands covering the full development lifecycle.

plan

Spec-driven planning. Turns a task description into testable acceptance criteria, vertical slices, and a TDD plan.

Produces
PRD.md / SPEC.md

build

Slice-by-slice TDD execution. Red, green, refactor — one slice at a time. Debug and refactor modes included.

Produces
tested, committed code

review

Parallel specialist reviewers for code quality, security, and accessibility. Findings only — no edits made.

Produces
findings-report.md

ship

Generate a conventional commit from staged changes. Use --pr to open a pull request.

Produces
git commit

status

Read-only dashboard of active work. Shows current phase, open specs, and last review findings.

Produces
dashboard output

help

Context-aware tour of available commands. Describe your task and get a recommendation for where to start.

A task, start to finish

One example task carried through all four phases. This is what fellowship produces.

1 Plan /fellowship:plan 
## Acceptance Criteria

### Slice 1: Add rate limiting to /api/ingest
GIVEN a request arrives at /api/ingest
WHEN  the caller has exceeded 100 req/min
THEN  the endpoint returns HTTP 429 with Retry-After header
  AND  the request is not processed

### Slice 2: Allow-list bypass
GIVEN the caller IP is in the allow-list
WHEN  the rate limit would otherwise be exceeded
THEN  the request is processed normally
2 Build /fellowship:build 
Slice 1/2: Rate limiting
RED confirmed: test_rate_limit_exceeded fails — handler returns 200, not 429
Writing minimal handler: check Redis counter, return 429 if exceeded
GREEN confirmed: 4 tests pass.
No refactoring needed. Suite green.

Slice 2/2: Allow-list bypass
RED confirmed: test_allowlist_bypass fails — allow-list not checked
Writing allow-list lookup before rate check
GREEN confirmed: 6 tests pass.
3 Review /fellowship:review 
## Findings

| # | Severity | Category     | File              | Finding                             |
| 1 | MEDIUM   | Security     | rate_limit.py:14  | Redis key not namespaced per-tenant |
| 2 | LOW      | Code Quality | rate_limit.py:22  | Magic number 100 should be config   |

## Summary
2 findings: 0 HIGH, 1 MEDIUM, 1 LOW
PASS — address MEDIUM before merge
4 Ship /fellowship:ship 
feat(api): add per-caller rate limiting to /api/ingest

- Returns HTTP 429 with Retry-After header when limit exceeded
- Allow-listed IPs bypass rate check
- Redis key namespaced per tenant (addresses review finding #1)
- Limit configurable via RATE_LIMIT_RPM env var

Closes #412
